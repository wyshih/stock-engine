  逐筆對帳（最大差 1e-7）
- `labels_ab/labels_ab.parquet` — 含 `sigma20` / `mfe20` / `excess20` / `label_A` / `label_B`

### 7% label 的結果與兩個紅旗

2024 年（現行系統最痛的一年）：新 label 模型 **+3.5~4.4%**，現行 r2_rf@0.47 是 **−1.58%**，
同期全買 −0.98%。方向正確。

**但結論還不能定案**：
1. **平均持有 127 個交易日**（中位 78 天）—— 遠超一個月 embargo。訓練期末端樣本的
   答案落在驗證期裡，val 段的 AUC 與門檻曲線都被污染。只有 test(2024) 距訓練
   結束 13 個月相對乾淨。**要繼續得把 embargo 拉到 6~12 個月重跑。**
2. **右設限偏誤逐年惡化**：未定比例 2020 年 0.5% → 2024 年 4.7% → 2025 年 14.4%
   → 2026H1 **47.5%**。活下來的都是「走得快的」，會系統性推高近期基準率。

## ⚠️ v3 三組模型無法逐欄重現（2026-08-22，搬進 engine repo 時發現）

**結論：m3 / m4 / m5 / m8 / m9 / m10 重建後拿到的特徵數是 518 / 506 / 490，
不是封存 bundle 的 509 / 497 / 481。base 的 m1 / m2 / m6 / m7（344 / 332）不受影響。**

| 特徵集 | 封存 bundle | 用現行官方資料重建 | 差 |
|---|---|---|---|
| base | 344 | 344 | — |
| nomkt | 332 | 332 | — |
| v3 | 509 | 518 | +9 |
| v3nomkt | 497 | 506 | +9 |
| v3nomv | 481 | 490 | +9 |

**原因不是程式被改壞。** `features/v3/spec.py` 與 `transforms.py` 與舊 repo
byte-identical（已 `cmp` 驗過）。真正的原因是 v3 的「sz / raw 變體要選哪一個」
依賴 `data/feature_audit.csv`，而那份稽核檔是**資料相依**的 —— 它用當時的全市場
資料算 Spearman 相關來分類特徵。換成 TWSE/TPEx 官方資料源之後，有 8 個特徵的
分類翻轉，另外多出 `bb_upper_break_log_xs` 等 `_log_xs` 欄。

**這代表什麼**：v3 那六個模型只能重新訓練出「同一套方法、新資料下的版本」，
不能宣稱是封存 bundle 的重現。拿新舊 v3 模型的績效直接對比是**不合法的比較** ——
特徵集不同、訓練資料也不同，兩個變因混在一起。

**怎麼確認自己踩到這件事**：`make verify-vs-old` 會印出上面那張對照表，v3 三組
標 📌（已知差異，不判 FAIL），base 兩組若也漂移則是真的有問題，要查。

## 已知的方法論陷阱（踩過的坑）

- **固定百分比門檻會製造波動度偏誤**：P(未來20日最大漲幅>7%) 從最低波動組 20.9%
  到最高波動組 66.0%，Spearman +0.316。除以 σ 後降到 −0.13。
- **分數不可跨 label 比較**，AUC 也不可 —— 基準率與問題難度都不同。最後只有
  同一套回測下的實際報酬能比。
- **門檻每次重訓都要重挑**，絕對值搬不動。方法固定：驗證期預測機率由高到低，
  **每一個機率值都當一次門檻**跑一遍，畫曲線由人看圖挑，不用「取前 N%」或任何
  自動規則。回測一律呼叫 `backtest.py` 的 `simulate()`/`performance()`，`dedup=False`。
- **不要並行訓練**：10 核機器，RF 內層已吃 6 核。三件同時跑 load average 衝到 23，
  互相搶資源反而每件都變慢（2026-08-14 實測）。
